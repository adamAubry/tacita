# SPEC 08 — Pipeline média

**Package : `packages/media-pipeline/`. Dépendances : spec 04 (Session, pour upload/download), DECISIONS D-03/D-04. Zéro DOM (les APIs navigateur — canvas, MediaRecorder — sont injectées/mockables).**

## Livrable

**Un seul pipeline d'upload pour tous les types de fichiers** (photos, vidéos, ZIP, PDF, bureautique, vocaux) — aucun canal parallèle. Chaîne : (compression si média) → chiffrement client → upload blob opaque → événement chiffré portant les clés. Et la chaîne inverse au téléchargement.

## Exigences et critères d'acceptation

- **REQ-MED-01** — Chiffrement côté client avant upload : AES-CTR, avec clé, IV et hash SHA-256 transportés dans l'événement chiffré (schéma `EncryptedFile` de la spec Matrix). Le serveur/S3 ne reçoit que des blobs opaques.
- **REQ-MED-02** — Tous les types de fichiers (ZIP, PDF, bureautique inclus) passent par ce même pipeline ; seuls images/vidéos/audio ont une étape de compression/transcodage en amont.
- **REQ-MED-03** — Vignettes générées **côté client** avant upload, chiffrées **séparément** (le serveur ne peut pas redimensionner un blob qu'il ne sait pas déchiffrer). Interdit d'appeler `/_matrix/media/*/thumbnail` sur un média chiffré.
- **REQ-MED-04** — Compression automatique et adaptative images/vidéos avant envoi, seuils DECISIONS D-04 (2 profils réseau, fallback « bon réseau »). Entièrement à développer, aucun mécanisme natif Matrix. *(**Amendée le 20/08/2026 — E-18.** Une source vidéo **déjà conforme** aux cibles D-04 est **remuxée, pas réencodée** : le réencodage n'est dû que par ce qui dépasse les cibles, et l'imposer à ce qui les respecte coûte une génération de perte et une attente, pour rien. **Conséquence sur l'UI, qui est une obligation de cette REQ et non une préférence du shard** : le remuxage ne demande aucun encodeur, donc le prédicat qui conditionne l'affichage du bouton d'envoi vidéo devient vrai sur des appareils où une source **non** conforme échouera quand même. L'échec de compression doit alors porter un **message dédié** — « impossible de compresser cette vidéo sur cet appareil » — distinct de l'absence de bouton. Sans lui, le prédicat promet plus que ce que le pipeline tient : c'est l'interdit n°13 pris par le mauvais bout.)*
- **REQ-MED-05** — Capture in-app photo/vidéo : l'original **non compressé** est sauvegardé sur l'appareil de l'auteur (File System Access / téléchargement selon support), fonction locale distincte de l'envoi ; le destinataire ne reçoit que la version compressée. *(**Portée amendée le 20/08/2026 — E-18.** La dernière phrase vise **le chemin de capture in-app**, celui que la REQ décrit, et lui seul ; l'envoi d'un fichier déjà présent sur l'appareil relève des cibles D-04. Écrite sans portée, elle se lisait comme une obligation de réencoder tout ce qui sort, et interdisait donc le remuxage d'une source déjà conforme. **La propriété protégée devient le conteneur normalisé unique en sortie** — ce qu'elle protégeait mal, faute de le nommer. Conséquence exacte : le remuxage sans réencodage est **conforme** ; le passthrough brut du fichier source ne l'est **pas**, et reste interdit — republier tel quel un `.mov` HEVC ferait sortir du pipeline un conteneur que rien n'a normalisé, et casserait la lecture chez une bonne partie des clients.)*
- **REQ-MED-06** — Messages vocaux : Ogg/Opus, convention `m.audio` (avec forme d'onde et durée dans le contenu de l'événement). Le calcul de forme d'onde fait partie du pipeline.
- **REQ-MED-07** — Sortie Ogg/Opus quel que soit ce que produit `MediaRecorder` (DECISIONS D-03), sans quoi les vocaux iPhone sont illisibles par les clients Matrix standards. Trois chemins d'entrée, trois coûts distincts : Ogg/Opus direct (Firefox) → rien à faire ; flux Opus en conteneur WebM (Chrome/Edge) → **remuxage** WebM → Ogg ; MP4/AAC (Safari/iOS) → **encodage** Opus, seul cas qui en demande un. *(Rédaction du 06/08/2026, E-10 : la version initiale imposait « transcodage WASM » sur les trois chemins.)*
- **REQ-MED-08** — **Aucun octet n'est servi, rendu ou écrit avant d'avoir été couvert par une vérification d'intégrité réussie.** Échec ⇒ `MediaIntegrityError`, aucun repli « meilleur effort », aucun octet livré — ni au lecteur, ni au disque, ni à un cache. Deux implémentations sont conformes : **(a) hash global** — SHA-256 du chiffré entier vérifié avant tout déchiffrement ; c'est le mécanisme actuel, et le seul interopérable avec les clients tiers ; **(b) hachage par blocs** — chaque bloc vérifié avant d'être déchiffré et remis au lecteur. (b) est un **durcissement** de (a), pas une dérogation : on passe de « on vérifie une fois un gros bloc » à « on vérifie chaque octet avant de le servir ». *(**Reformulée le 20/08/2026 — E-23.** La rédaction précédente — « Téléchargement : récupération du blob, vérification du hash SHA-256, déchiffrement local. Hash invalide → média rejeté avec erreur explicite. » — décrivait un **mécanisme**, pas une propriété. Écrite ainsi, elle rendait le hachage par blocs formellement non conforme alors qu'il renforce exactement ce qu'elle protège. La REQ dit désormais la propriété ; les mécanismes sont énumérés dessous, et un troisième s'y ajouterait sans ré-amender la REQ.)*

  > **Ce que ce modèle authentifie, et par quoi.** SHA-256 n'est pas un MAC, et AES-CTR est malléable : le hash seul n'authentifie rien, il détecte une corruption. Ce qui authentifie le fichier, c'est que **le hash et la clé voyagent tous deux dans l'événement chiffré par Megolm** — l'intégrité est obtenue par **transitivité via l'enveloppe**, jamais localement. Propriété non locale, à relire avant d'ouvrir tout nouveau chemin : un mécanisme qui référencerait un fichier chiffré **hors** d'un événement chiffré — lien de partage, notification enrichie, cache d'aperçu, export — ferait disparaître la garantie sans qu'une seule ligne du module de chiffrement ait changé.
- **REQ-MED-09** — Compatibilité authenticated media : le module consomme les URLs média selon le comportement consigné par l'infra (spec 01, REQ-INF-12) ; aucune URL média publique n'est supposée.
- **REQ-MED-10** — Aucun contenu média en clair (ni ses clés) dans les logs ou traces d'erreur du module.
- **REQ-MED-11** — **L'unique chemin public du pipeline** : `uploadPublicProfileImage()` téléverse une photo de profil **non chiffrée**, un avatar Matrix devant être un `mxc://` nu que tout client puisse afficher. Même paquet, même compression, même point d'entrée que le reste — l'interdit n°11 (un seul pipeline) tient. Trois conditions, toutes vérifiables : le nom de la fonction dit `Public` ; **une liste close de sites d'appel** dans tout le dépôt — le formulaire de profil de M-G et le câblage des images par défaut (REQ-MSG-22) —, gardée par un test structurel qui balaie les sources et compare la liste **à l'identique**, donc échoue sur toute entrée non relue ; et l'UI dit au moment du choix que la photo n'est pas chiffrée. La promesse du module devient « tout ce qui sort du pipeline est chiffré, **sauf l'unique chemin nommé public** » — la précision n'a de valeur que parce que le test empêche la dérive. La **bannière** (REQ-MSG-21, REQ-UIX-41) emprunte cette même fonction : deux images publiques, même compression, et surtout **toujours un seul site d'appel** — le formulaire les fait passer par le même callback injecté, ce qui laisse le test structurel intact. `downloadPublicImage()` en est le pendant en lecture : un `mxc://` non chiffré rendu en `Blob` par un `fetch` **authentifié**, parce que les endpoints média anonymes répondent 404 (REQ-INF-12) et qu'une balise `img` ne sait pas porter d'en-tête `Authorization`. Sans lui, une photo correctement téléversée reste invisible — ce fut le cas jusqu'au 10/08/2026. *(Ajoutée le 07/08/2026 — escalade E-12, voie A. Chiffrer un avatar en fait un carré cassé chez tous les clients : c'est une non-feature, pas une garantie. Étendue le 10/08/2026 au chemin de lecture et à la bannière. **Second site d'appel admis le 11/08/2026** — les images par défaut de REQ-MSG-22 : mêmes images publiques, même fonction, même compression, et l'unicité qui protégeait vraiment était celle de la *fonction*, pas du nombre d'appelants. Le test reste une égalité de liste, pas un plafond de compte.)*
- **REQ-MED-12** — **Liste close des types rendus — vidéo et image.** Le type d'un média reçu se résout dans cet ordre : `info.mimetype` de l'événement ; à défaut — champ absent, vieux clients, ponts — **sniffing des octets d'en-tête du clair** (`ftyp` à l'offset 4 pour MP4/MOV, `1A 45 DF A3` à l'offset 0 pour Matroska/WebM, signatures usuelles pour les images). Le type résolu n'est rendu que s'il appartient à la liste close ci-dessous ; hors liste ⇒ **aucun rendu, aucun object URL de ce type**, l'action offerte est le téléchargement.

  | Chemin | Types rendus |
  |---|---|
  | Vidéo | `video/mp4`, `video/quicktime`, `video/webm`, `video/x-matroska` |
  | Image | `image/jpeg`, `image/png`, `image/webp`, `image/gif`, `image/avif` |
  | Audio | `audio/ogg`, `audio/mpeg`, `audio/mp4`, `audio/webm`, `audio/wav` |

  *(**Ligne audio ajoutée le 20/08/2026, à l'implémentation.** La REQ était écrite pour deux chemins ; le shard en rend **trois** — `m.audio` passe par la même fonction de téléchargement et le même `URL.createObjectURL` que les deux autres, avec le même `info.mimetype` fourni par l'expéditeur. Laisser l'audio hors de la liste aurait laissé le trou ouvert sur le tiers du problème, et la garde est unique : elle vit à l'endroit par où passent les trois. `audio/ogg` est notre format de sortie unique (D-03) ; les quatre autres sont ce qu'un client tiers ou un pont peut envoyer.)*

  Trois précisions font la REQ :
  - **`application/octet-stream` n'est pas un type rendable.** C'est le repli actuel du chemin de lecture, et il échoue en silence : un Blob de ce type dans un `<video>` ne joue pas et ne dit pas pourquoi. L'échec de résolution est un **état explicite**, jamais un repli.
  - **Le support du codec est vérifié avant d'afficher un lecteur** (`canPlayType`, ou `MediaSource.isTypeSupported` quand le codec précis est connu) : réponse vide ⇒ message explicite et téléchargement, jamais un rectangle noir. Le HEVC d'iOS lit sur Safari et pas partout ailleurs ; sans ce contrôle, l'utilisateur conclut que l'application est cassée.
  - **Pourquoi une liste close, et par défaut de refus.** `info.mimetype` est protégé par Megolm : non falsifiable par le serveur, **parfaitement falsifiable par l'expéditeur** — le chiffrement ne protège rien ici. `image/svg+xml` n'exécute pas de script dans un `<img>`, mais c'est un parseur complet nourri d'octets choisis par un tiers, et la liste close coûte cinq lignes. Elle s'écrit comme celle de REQ-UI-02 : ce qui n'est pas nommé est refusé, sinon le prochain type ajouté passera au vert faute d'avoir été relu. *(Créée le 20/08/2026 — E-19. Aucune REQ ne disait ce qu'on avait le droit de mettre dans un Blob rendu, et le trou était ouvert en production : `info.mimetype` alimente déjà le Blob côté vidéo comme côté image.)*
- **REQ-MED-13** — **Piste audio des vidéos envoyées.** AAC-LC (`mp4a.40.2`), débit et fréquence d'échantillonnage fixés par D-04. Source muette ⇒ fichier **mono-piste**, jamais de piste vide. **AAC indisponible sur la plateforme ⇒ la vidéo part muette, avec mention explicite dans l'UI** ; **aucun repli vers un autre codec audio ou un autre conteneur n'est autorisé** — ni Opus-in-MP4, ni autre chose, quelle qu'en soit la disponibilité apparente. Un conteneur dont l'interop n'a pas été mesurée contre Element Web, iOS et Android produit un fichier que le destinataire ne lit pas : c'est pire que le silence, et c'est l'interdit n°13. Conformité : dérive audio/vidéo **inférieure à 50 ms au bout de 5 minutes**, mesurée sur fichier d'or. *(**Moyen amendé le 20/08/2026, à l'implémentation.** La REQ prévoyait un **encodage** AAC-LC par `AudioEncoder`, et le repli muet pour le cas « AAC indisponible sur la plateforme ». Le pipeline ne convertit finalement **aucune** piste sonore : il **recopie** celle de la source quand elle est déjà de l'AAC — ce qui est le cas de toutes les caméras de téléphone —, et part muet sinon. Trois raisons, dans cet ordre : une piste AAC recopiée est identique à ce qu'un encodage aurait produit, en mieux, puisqu'elle ne perd pas une génération ; un encodeur audio ne se teste dans aucun environnement de ce dépôt, alors que la recopie se prouve de bout en bout par le muxeur et le démuxeur ; et un encodeur non éprouvé aurait produit des fichiers dont l'interop n'est vérifiée nulle part, ce que la REQ interdit dans sa phrase suivante. **La condition du repli muet change donc de nature** : ce n'est plus « cette plateforme ne sait pas encoder » mais « le son de cette source n'est pas transportable tel quel ». L'obligation de le dire, elle, ne change pas. Encoder une piste non-AAC reste à faire, et cette REQ reste son contrat.)* *(Créée le 20/08/2026 — E-20. **D-03 ne s'applique pas ici** : elle porte sur les messages vocaux `m.audio`, dont le format de sortie unique tient à l'interop de client à client. La piste audio d'une vidéo est un autre objet, gouverné par D-04. Écrit parce que rien ne le disait, et qu'« AAC » à côté de « D-03 » se lit comme une violation.)*
- **REQ-MED-14** — **L'orientation perçue de la source est celle du fichier de sortie.** Voie préférée : **propager la matrice de transformation dans le `tkhd` de sortie** — gratuit, sans perte, et c'est ce que fait la source. Si l'orientation est cuite dans les pixels, `w` et `h` sont échangés en conséquence. Dans les deux cas, `info.w`/`info.h` de l'événement restent cohérents avec le fichier livré. Conformité : fichier d'or, **quatre orientations**. *(Créée le 20/08/2026. Aucune règle ne couvrait l'orientation, et le comportement correct était **accidentel** : le chemin actuel passe par un canvas, qui rend la frame *affichée*, matrice appliquée. Un chemin décodeur → encodeur direct rend la frame *codée*, matrice non appliquée — la refonte introduirait donc une régression que rien dans le dépôt ne détecte. La REQ existe pour que le fichier d'or existe.)*
- **REQ-MED-15** — **Deux plafonds de taille en réception, lus dans `info.size` avant tout téléchargement.**
  - **`SEUIL_INLINE`** — au-delà, aucun lecteur n'est proposé ; l'action offerte est le téléchargement.
  - **`SEUIL_DUR`** — au-delà, refus explicite et motivé (« fichier trop volumineux pour cet appareil »). Ce second plafond **ne s'applique que lorsque le téléchargement en flux est indisponible**, c'est-à-dire quand le fichier entier doit tenir en mémoire.

  Les deux sont abaissés sur mobile, et la décision est une **fonction pure**, testable sans UI. Ce qui rend ces plafonds nécessaires : `crypto.subtle.digest` est **one-shot** — WebCrypto n'expose aucun hash incrémental —, donc vérifier avant de déchiffrer impose de tenir tout le chiffré en mémoire (REQ-MED-08, mécanisme (a)). **AES-CTR, lui, est seekable** : le déchiffrement peut se faire par tranches. Le schéma « **une vérification globale, puis déchiffrement par tranches écrites au fur et à mesure** » est donc explicitement conforme à REQ-MED-08, et divise le pic mémoire — c'est le chemin d'un téléchargement. Enfin, **le clair écrit lors d'un téléchargement va directement à la destination choisie par l'utilisateur**, jamais dans un stockage de notre origine : pas de staging OPFS, pas de fichier temporaire. *(Créée le 20/08/2026. Sans elle, une vidéo de 400 Mo reçue d'un client tiers fait coexister chiffré, clair et Blob — environ trois fois la taille du fichier — et tue l'onglet sur mobile.)*
- **REQ-MED-16** — **Cache local de ciphertext.** Le cache persiste **le chiffré, et lui seul** : aucun octet en clair ne touche un stockage persistant (interdit n°8, REQ-MED-10). Éviction LRU, budget total configurable. **Le store s'inscrit au registre de wipe** (spec 04, REQ-COR-10), comme le font REQ-OBX-08 et REQ-SRC-08. Motif de l'inscription : un cache qui survit à la déconnexion n'est pas une fuite de contenu — il est inerte sans les clés Megolm — mais c'est une trace de qui a échangé quoi et quand, sur une machine partagée. Conformité : `wipe()` ⇒ store vide ; et un relevé du store après une lecture de média qui n'y trouve **aucun octet en clair**. *(Créée le 20/08/2026 — E-21.)*

- **REQ-MED-17** — **L'étape de téléversement est exposée à part, idempotente, et sans retry propre.** Le pipeline expose le téléversement d'un chiffré **déjà produit** comme une étape rejouable : rejouée avec le même chiffré, elle ne rechiffre rien et ne régénère rien — ni clé, ni IV, ni hash. **Le pipeline ne retente jamais de lui-même** : la reprise appartient à la file d'envoi (spec 07, REQ-OBX-10). **Limite de l'idempotence, à ne pas surestimer : elle est côté application, pas côté serveur.** L'API media de Matrix n'offre aucune clé d'idempotence ; un téléversement réussi dont la réponse se perd laisse un blob orphelin, et le rejeu en crée un second. C'est acceptable — un blob orphelin est un blob opaque de plus, que jamais aucun événement ne référence — mais c'est écrit, sinon « idempotent » se lira comme une propriété de bout en bout. *(Créée le 20/08/2026 — E-22.)*

- **REQ-MED-18** — **Lecture progressive par hachage par blocs, et les bornes qu'elle impose au service worker.**

  Le chiffré d'un média envoyé par Tacita est haché **par blocs de 1 MiB**, et la liste des empreintes voyage dans le contenu de l'événement — donc sous Megolm, comme `hashes.sha256`, que l'on continue d'écrire. Le champ est **namespacé `org.tacita.*`**, documenté comme nôtre, et **jamais présenté comme du Matrix natif** (même discipline que l'accusé « délivré », interdit n°9). En réception : champ présent ⇒ chemin progressif ; absent ⇒ chemin d'un seul bloc, **inchangé**. Aucune régression avec un client tiers.

  Ce que ça achète : la première image d'une vidéo n'attend plus qu'un bloc soit vérifié et déchiffré, au lieu du fichier entier. Ce que ça ne cède pas : **chaque bloc est vérifié avant d'être déchiffré et servi** — c'est le mécanisme (b) de REQ-MED-08, un durcissement de (a) et non une dérogation. Un bloc invalide interrompt la lecture, ne rend aucun octet de ce bloc ni des suivants, et remonte `MediaIntegrityError`. **La fausse solution est nommée pour être refusée : calculer l'empreinte au fil de l'eau et invalider à la fin sert des octets non vérifiés, et vide REQ-MED-08 de son sens.**

  **Les bornes du service worker font partie de la REQ, pas des commentaires.** Il n'y a qu'un worker par portée : celui qui sert les médias **est** celui du push, réveillé hors de toute page. Lui confier des clés en ferait un composant capable de déchiffrer hors du cycle de vie d'un onglet. La forme retenue est plus forte que des bornes sur une table de clés — **il n'y a pas de table, parce qu'il n'y a pas de clés** :
  - le worker ne déchiffre rien, ne détient aucune clé et aucune empreinte ; il **demande** les octets d'une plage à une fenêtre vivante, qui vérifie et déchiffre ;
  - aucune fenêtre à qui demander ⇒ **404**, jamais un octet servi. Un worker démarré à froid par une notification est donc muet par construction ;
  - le clair traverse le worker sans y séjourner : **jamais de `caches.put`**, et la réponse porte `no-store` pour que le navigateur ne le range pas non plus (interdit n°8, REQ-UI-01) ;
  - l'URL virtuelle est **non devinable** et vit dans la mémoire de la page qui l'a inscrite : elle meurt avec elle.

  Conformité : un worker démarré à froid ne sert aucune plage tant qu'aucune fenêtre n'a inscrit de média ; un bloc corrompu artificiellement interrompt la lecture sans rendre d'octet ; un média sans le champ propriétaire suit le chemin legacy. *(Créée le 20/08/2026 — E-23. Prérequis : `moov` en tête, sans quoi un lecteur doit lire la fin du fichier avant la première image.)*


## Méthode et contraintes

- WebCrypto pour AES-CTR/SHA-256 ; canvas/OffscreenCanvas pour vignettes et compression image.
- **Encodage dans le shard, empaquetage dans le paquet** (E-10, 06/08/2026). Les APIs qui encodent vivent chez l'utilisateur et entrent par le `MediaEnvironment` injecté : `MediaRecorder` pour l'audio, `WebCodecs` pour la vidéo. Les **muxeurs** — Ogg pour l'audio, MP4 pour la vidéo — sont octets → octets, sans DOM : ils vivent **ici**, dans ce paquet, écrits à la main, sans dépendance. La contrainte « zéro DOM » du paquet est intacte : un muxeur ne touche à rien.
- **« Sans dépendance » s'ouvre — pour le conteneur, et pour lui seul** (E-17, 20/08/2026). La clause ci-dessus a été écrite quand le seul conteneur à produire était le nôtre. Elle bloque le **démuxage** d'un fichier entrant, qui est un tout autre problème : les sources viennent de toutes les caméras du marché — listes d'édition, pistes multiples, `moov` fragmenté, rotation dans le `tkhd`, `.mov` HEVC d'iPhone —, et un démuxeur maison sur cette surface est un puits à défauts d'interop. **Ce paquet peut donc porter des dépendances runtime de démuxage et de muxage de conteneur**, sous le régime de `CLAUDE.md` § Prudence outillage, règle 5 : **version épinglée, digest consigné, CHANGELOG relu avant tout bump** — exactement le traitement d'Astryx.

  **Ce que cet amendement ne fait pas, et c'est le cœur de l'amendement.** Il n'ouvre rien d'autre. La séparation E-10 — *encodage dans le shard, empaquetage dans le paquet* — reste **intacte**, et le paquet reste **testable sans globales navigateur**. Une bibliothèque qui piloterait `WebCodecs` elle-même — donc qui encoderait depuis le paquet — reste exclue par E-10 : elle demanderait de rouvrir E-10 séparément, et cet amendement-ci ne l'autorise pas. La contrainte « zéro DOM » n'est pas levée non plus : un démuxeur prend des octets et rend des octets, comme un muxeur.

  **Aucune bibliothèque n'est nommée ici** : le choix est d'implémentation, il vit dans le plan et dans le lockfile. La spec dit le régime, pas le fournisseur.
- **Repli WASM, seulement si mesuré nécessaire.** Si `WebCodecs AudioEncoder` n'accepte pas `opus` sur les versions d'iOS ciblées, un encodeur Opus WASM entre — **dans ce paquet, pas dans `apps/web`** (REQ-UI-02 reste close). Un encodeur est octets → octets au même titre qu'un muxeur. Ne pas l'ajouter avant que le spike E-10 l'ait rendu nécessaire.
- Les opérations lourdes (transcodage, compression vidéo) tournent en Web Worker — jamais sur le thread principal.
- Hors scope : UI de capture, galerie, lecteur (spec 11) ; file d'envoi (spec 07 — le pipeline produit un contenu prêt à `enqueue`). *(**Portée amendée le 20/08/2026 — E-22.** « File d'envoi hors scope » laissait la **reprise d'un téléversement interrompu** sans propriétaire : la spec 07 possède les retries d'**événements**, celle-ci met la file hors scope, et un envoi de 200 Mo qui échoue à 90 % n'était réessayé par personne. Deux specs respectées, le trou entre elles — le motif exact de la règle 1. La reprise appartient désormais à la file (REQ-OBX-10) ; ce paquet expose l'étape idempotente qu'elle rejoue (REQ-MED-17) et ne retente rien lui-même.)*

## Objectif mesurable
