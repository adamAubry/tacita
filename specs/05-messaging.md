# SPEC 05 — Domaine messagerie (headless)

**Package : `packages/messaging/`. Dépendances : spec 04 (Session). Zéro DOM.**

## Livrable

API métier des conversations texte : DM et groupes, envoi/réception chiffrés, réponses, réactions, édition/suppression, épinglage, copie, typing, mentions. Expose des fonctions pures + observables consommés par le shard UI (spec 11).

## Exigences et critères d'acceptation

- **REQ-MSG-01** — Envoi et réception de messages texte chiffrés (`m.room.message` en salon chiffré) via la Session (spec 04).
- **REQ-MSG-02** — Création de DM (salon à 2, `is_direct`) et de group chats. Tous chiffrés dès la création (garanti serveur par spec 01, vérifié client : refus d'envoyer dans un salon non chiffré).
- **REQ-MSG-03** — Déduplication d'envoi par `txnId` généré côté client, mécanisme **natif** du SDK — ne rien construire par-dessus. Critère : rejouer la même requête produit le même `event_id`.
- **REQ-MSG-04** — Réponse à un message via relation `m.in_reply_to`.
- **REQ-MSG-05** — Réactions emoji (`m.annotation`), visibles de tous. Le module expose la métadonnée `cleartext: true` et la doc précise : les réactions circulent en clair en salon chiffré — les chiffrer casserait l'agrégation serveur ; le serveur voit qui réagit à quoi. **Lecture comprise** : les réactions d'un message sont exposées agrégées (emoji, compte, « la mienne »), redactions exclues. *(Ajouté le 05/08/2026 : le module savait envoyer une réaction sans savoir la relire, et le shard aurait dû fouiller les relations du SDK lui-même — de la logique métier dans la spec 11. Envoyer sans afficher aurait aussi été une moitié de fonctionnalité, contraire à l'interdit n°13.)*
- **REQ-MSG-06** — Modification (`m.replace`) et suppression (redaction) d'un message ; l'API expose « modifiable/supprimable » par message (droits + auteur).
- **REQ-MSG-07** — Extraction du texte d'un message pour copie (fonction pure ; l'accès presse-papiers est dans l'UI).
- **REQ-MSG-08** — Épinglage via `m.room.pinned_events`, avec métadonnée exposée et documentée : événement d'état **non chiffré**.
- **REQ-MSG-09** — « Est en train d'écrire » via l'EDU éphémère `m.typing` : aucun événement de frappe en base, **throttling côté client** (une émission max toutes les N secondes, pas d'émission par frappe), timeout d'arrêt automatique. **Lecture comprise** : qui écrit dans un salon, soi-même exclu, et son observable. *(Ajouté le 05/08/2026, même motif que REQ-MSG-05 : le module n'émettait que dans un sens, et REQ-UI-11 demande l'indicateur en lecture.)*
- **REQ-MSG-10** — Mentions type Discord : syntaxe `@everyone` mappée sur `@room` (push rule native `.m.rule.roomnotif`) ; le module fournit le parsing de la syntaxe et les données d'autocomplétion (membres du salon + `@everyone`). Le rendu est dans l'UI.
- **REQ-MSG-11** — Rôles : échelle numérique de power levels Matrix telle quelle — pas de rôles nommés, pas d'héritage par catégorie. Le module expose lecture/écriture des power levels et le compteur de membres du salon.
- **REQ-MSG-12** — L'ordre des messages exposé est celui de `OrderedTimeline` (spec 04) ; ce package n'introduit aucun tri propre.
- **REQ-MSG-13** — Liste des conversations : salons rejoints (DM et groupes) avec nom, dernier message, horodatage, compteurs **natifs** de non-lus et de mentions, marque d'épingle ; invitations en attente exposées à part (D-09 : une demande d'ami *est* une invitation de DM) ; observable branché sur l'émetteur du SDK. **L'ordre rendu est la récence du dernier message** — voir la réserve ci-dessous.
- **REQ-MSG-14** — Épinglage d'une conversation par le tag natif `m.favourite` (lecture et écriture). Synchronisé par le serveur comme toute account data de salon, donc **visible de lui** : métadonnée, jamais du contenu.
- **REQ-MSG-15** — Ouverture d'un DM avec un utilisateur : le DM existant est réutilisé, un second n'est **jamais** créé. Un DM quitté ne compte pas comme existant.
- **REQ-MSG-16** — Cycle de vie d'une relation, par les membres de salon natifs (D-09) : accepter une demande d'ami est un `join` sur le DM invité, la refuser un `leave`, retirer un ami un `leave` également. Aucun registre d'amitié n'est écrit en plus — il n'en existe pas.
- **REQ-MSG-17** — Blocage par `m.ignored_user_list` natif : lecture, ajout et retrait, l'écriture relisant la liste courante plutôt que de tenir un cache. **L'effet réel est borné et doit être exposé tel quel** (interdit n°13) : le serveur cesse de nous *envoyer* les événements de la personne ; elle n'est ni empêchée d'écrire, ni prévenue, et reste membre des salons partagés.
- **REQ-MSG-18** — Profil : lecture du profil public d'un utilisateur (nom d'affichage, `mxc://` d'avatar), avec repli sur l'identifiant quand le compte n'a pas de nom ou que la lecture échoue — un profil absent n'est pas une erreur d'écran ; écriture de son propre profil, champ par champ, pour qu'une modification partielle n'efface pas ce qu'elle ne touche pas.
- **REQ-MSG-20** — **Sas d'entrée par `knock`** : lecture et écriture de `m.room.join_rules` (`invite` ⇄ `knock`), émission d'un `knock`, et liste de ceux qui attendent. Accepter quelqu'un qui a frappé est une **invitation native** (REQ-MSG-11), pas un mécanisme de plus. `createGroupChat` reste en `join_rule: invite` par défaut : la bascule est portée par le cycle de vie des liens (spec 12, M-H), jamais par la création. Un salon dont l'état est illisible ou absent compte comme `invite` — dans le doute, fermé. *(Ajoutée le 07/08/2026 — escalade E-13, voie A. Sans elle, un lien de groupe résolvait un `roomId` que son porteur ne pouvait ni rejoindre ni se faire inviter.)*
- **REQ-MSG-21** — **Bannière de profil**, en champ de profil **étendu** (MSC4133) nommé `org.tacita.banner_url`, porteur d'un `mxc://` public au même titre que l'avatar. Matrix ne définit que `displayname` et `avatar_url` : une bannière n'existe nulle part dans la spec, et la poser dans l'account data la rendrait invisible aux autres — or elle est faite pour être vue. Lecture **sans requête supplémentaire** : `GET /profile/{userId}` rend les champs personnalisés avec le reste du profil ; écriture par `setExtendedProfileProperty`. Une valeur non textuelle est ignorée — le champ est libre côté serveur. *(Ajoutée le 10/08/2026. Vérifié contre le Synapse déployé, v1.155.0 : la route générique `PUT /_matrix/client/v3/profile/{userId}/{champ}` y est enregistrée sans condition et `uk.tcpip.msc4133.stable` est annoncé en dur — **l'infra n'a rien à changer**, `msc4133_enabled` n'ajoutant que le préfixe instable. À revérifier au prochain bump : une route inconditionnelle peut repasser derrière le drapeau.)*
- **REQ-MSG-22** — **Images de profil par défaut à la création du compte** : un avatar (style `glyphs`) et une bannière (style `constellation`) dessinés **sur l'appareil** par DiceBear, avec l'identifiant Matrix pour seed. Trois propriétés, toutes vérifiables : le dessin est **déterministe** (même compte → mêmes images, sans rien stocker) ; il est **local** — la bibliothèque rend du SVG, aucune URL de service n'est appelée, donc aucune règle d'épinglage de runtime externe n'entre en jeu ; et il **n'écrase jamais un choix**, les deux champs étant regardés séparément (une photo choisie sans bannière garde sa photo et reçoit sa bannière). Le téléversement n'est pas fait ici : la fonction reçoit un `televerser` injecté et rend deux `mxc://` au chemin public du pipeline (REQ-MED-11), ce qui laisse les sites d'appel de ce chemin comptables un par un. La dépendance DiceBear vit dans ce paquet, jamais dans `apps/web` — REQ-UI-02 tient sa liste close, même jurisprudence qu'E-10. *(Ajoutée le 11/08/2026. Sans elle, tout compte neuf ouvre sur des initiales et un aplat d'accent : les cartes de profil sont toutes identiques tant que personne n'a téléversé de photo.)*
- **REQ-MSG-19** — Recherche d'utilisateur dans l'**annuaire** du homeserver (`/user_directory/search`), qui porte des identifiants et des noms d'affichage. Sans rapport avec l'interdit n°3, qui vise `/search` (recherche de **contenu**, inopérant sur salon chiffré). Un terme vide ne déclenche aucun appel. **Un terme qui est un identifiant Matrix complet (`@nom:serveur`) se résout par lecture de profil, pas par l'annuaire** : Synapse n'y liste par défaut (`search_all_users: false`) que les comptes avec qui on partage déjà un salon, ce qui rend l'annuaire structurellement incapable de servir une première prise de contact. Un identifiant inconnu du serveur ne rend aucun résultat. *(Amendée le 07/08/2026 — mesuré contre un vrai Synapse : l'annuaire rendait `results: []` pour un compte existant pendant que la lecture de son profil rendait son nom. Sans ce chemin, « Ajouter par identifiant » ne trouvait jamais personne et aucune première conversation n'était possible. L'alternative — ouvrir l'annuaire à tout le serveur — exposerait chaque compte à tout autre.)*

> **Réserve portée par REQ-MSG-13, ajoutée le 05/08/2026 avec l'exigence.** L'interdit global « ne jamais trier par `origin_server_ts` » vise l'ordre des messages *dans* une timeline, où /sync fait autorité (REQ-COR-04, REQ-MSG-12) — et il reste entier. Mais une **liste de salons** n'a aucun ordre dans /sync : `getRooms()` rend l'ordre d'insertion du store. La récence du dernier message est le seul signal disponible côté client, et REQ-UIX-07 (tri récentes/anciennes) l'exige. Il est donc utilisé **ici seulement**, jamais à l'intérieur d'un salon. **Tranché en périmètre technique le 05/08/2026, PM informé** — le motif complet et les alternatives écartées sont dans `specs/ui/ESCALATIONS.md` § E-09.

## Méthode et contraintes

- Utiliser les APIs du SDK partout où elles existent ; ce package est une façade métier, pas une réimplémentation.
- Hors scope : accusés de réception (spec 06), file hors ligne (07), média (08), recherche (09), tout rendu.

## Objectif mesurable

Suite Vitest avec Session mockée : une describe par REQ, nommée par son ID. Points de contrôle notables : REQ-MSG-03 (double appel même txnId → un seul event) ; REQ-MSG-09 (20 frappes en 1 s → ≤ 1 émission m.typing, fake timers) ; REQ-MSG-10 (`"salut @everyone"` → contenu avec mention room conforme) ; REQ-MSG-05/08 (métadonnées `cleartext` présentes) ; REQ-MSG-13 (salon invité absent de la liste et présent dans les invitations ; compteurs natifs relayés tels quels) ; REQ-MSG-15 (DM existant → aucun `createRoom` ; DM quitté → création) ; REQ-MSG-17 (bloquer deux fois n'écrit qu'une fois ; la liste existante n'est jamais écrasée) ; REQ-MSG-18 (profil introuvable → repli sur l'identifiant, pas de levée ; ne changer que le nom n'appelle pas `setAvatarUrl`) ; REQ-MSG-21 (le champ étendu lu depuis la réponse de profil, sans appel de plus ; valeur non textuelle → `undefined` ; ne changer que le nom n'écrit aucun champ étendu) ; REQ-MSG-19 (terme vide → aucun appel réseau ; identifiant complet → lecture de profil et **aucun** appel à l'annuaire ; identifiant inconnu → aucun résultat) ; REQ-MSG-20 (bascule `invite` ⇄ `knock` écrite dans l'état ; état absent → `invite` ; ceux qui ont frappé sont lus depuis l'appartenance `knock`, jamais depuis les membres joints) ; REQ-MSG-22 (deux SVG distincts, identiques d'un appel à l'autre pour un même identifiant et différents d'un identifiant à l'autre ; profil déjà pourvu → aucun téléversement et aucune écriture ; avatar seul déjà posé → seule la bannière est téléversée).
